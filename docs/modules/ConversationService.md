# ConversationService и MentorPrompt

Связка библиотечных сервисов чата, контекста, LLM и дневника в `core` по решению 38.
Заголовки и реализации: `src/core/include/msa/core/ConversationService.h`,
`MentorPrompt.h`, `src/core/src/ConversationService.cpp`, `MentorPrompt.cpp`.
HTTP, JSON-разбора, Qt, таймеров и доставки клиентам здесь нет.

## Точки входа

- `offerEveningCheckIn` — запрашивает предложение у EveningCheckInService,
  сохраняет Assistant в текущем чате и ожидание в EveningCheckInRepository.
  Возвращает ID сообщения либо nullopt, если опрос не нужен.
- `sendMessage` — сохраняет полный User через ChatService и делает одну попытку
  ответа по явному общему бюджету кодовых точек Unicode.
- `retryLastMessage` — повторяет обработку последнего User без новой записи текста.
  Предназначен для явного повтора после ошибки LLM или недостаточного бюджета.
  Если последнее сообщение Assistant или история пуста — отказ.
- `MentorPrompt::build` — согласованные инструкции и JSON-формат с явным
  awaitingEveningCheckIn. Данные профиля и истории не заменяют эти правила.

Зависимости передаются через конструктор: Clock, ChatService, UserProfileService,
DailyContextService, LlmClient, MoodService, EveningCheckInService и его репозиторий,
общий TransactionRunner и WebSearchProvider.
Часы должны представлять одно серверное время, репозиторий опроса должен быть
тем же объектом, который передан EveningCheckInService. Сборщик контекста,
отбор фактов и генератор инструкций создаются локально и не хранят состояние.

## Обработка сообщения

1. Сохранить User полностью. При неверном вводе вернуть ConversationRejection
   без вызова LLM. При последующем отказе User остаётся в истории.
2. Прочитать историю и действующее ожидание. Выбрать факты по словам вопроса
   и ручным тегам через UserProfileFactSelector, получить сводку дня.
3. Передать MentorPrompt, факты, сводку и историю в LlmContextBuilder с общим
   бюджетом. Текущий вопрос исключается из истории по сохранённому ID.
4. Вызвать LlmClient ровно один раз. Ошибка возвращается без ответа Assistant,
   записи дневника или снятия неистёкшего ожидания. Автоматического повтора нет.
5. Проверить profileFacts через UserProfileService без записи, до действий с дневником.
6. Если есть проверенное предложение записи, вызвать MoodService с его оценкой
   и полной исходной заметкой. Только после успешной записи добавить к ответу
   «Настроение сохранено в дневник.» и вернуть ID записи.
7. Сохранить факты/версии с ID чата, User и созданной записи дневника, если она есть.
   После save добавить «Сохранено в памяти» и новые тексты; для повторов подтверждения нет.
8. Сохранить полный Assistant, снять ожидание в этом чате после успешной обработки.
   ConversationReply содержит текст, ID сообщения, тон, ID дневника и новых фактов.

Оценка тона возвращается для текущей реакции, но не записывается автоматически.
Сервис доверяет распознаванию намерения LLM после проверки структуры; словарный
анализ не добавлен. Для ясной просьбы вне опроса допустима ExplicitRequest.

По решению 39 факты сохраняются автоматически без отдельного запроса и подтверждения
каждой записи. Метки `[Факт ID=…]` актуальных фактов входят в бюджет. LlmRequest
разрешает замену только ID из включённого префикса. Старые версии профиля исключаются
из отбора; исходные сообщения остаются в истории. Промпт объясняет, что история
может содержать устаревшие сведения. Подробнее — [UserProfileService](UserProfileService.md).
Смысл факта пока проверяет модель, готового семантического распознавания нет.

## Состояние вечернего опроса

PendingEveningCheckIn в существующем EveningCheckInRepository содержит ID чата,
ID сообщения опроса и местную дату. Опрос один на день, поэтому хранится одно
необязательное ожидание, независимо от даты выдачи. Снятие ожидания не разрешает
повторную выдачу опроса в тот же день.

По сохранённой истории определяется первый User после сообщения опроса. Только
при его обработке в том же чате и в ту же дату awaitingEveningCheckIn=true.
Переключение чата не переносит и не потребляет ожидание. Отказ, другая тема
и неясная оценка закрывают его при успешном ответе без предложения записи.
Эту классификацию выполняет модель; сейчас тесты задают её результат явно.

При ошибке LLM первый User остаётся для retryLastMessage. Если вместо повтора
пользователь отправил новое сообщение, оно уже не первый ответ на опрос;
после успешной обработки в исходном чате ожидание закрывается без такого переноса.
Обычные явные просьбы о записи по-прежнему допустимы.

В другую календарную дату ожидание недействительно; физически очищается при
следующей проверке сервиса, в том числе после завершения запроса LLM. Если дата
сменилась во время запроса и модель предлагает запись EveningCheckInReply,
результат отклоняется без дневника/Assistant; User остаётся для явного повтора.
История опроса и ответа при истечении не удаляется.

Пересоздание ChatService и ConversationService поверх того же хранилища
восстанавливает ожидание. [SqliteEveningCheckInRepository](SqliteEveningCheckInRepository.md)
сохраняет дату выдачи и PendingEveningCheckIn между открытиями SQLite-файла.
ServerRuntime открывает базу из настроек. Запись ответа использует общий TransactionRunner;
публикация опроса выполняется отдельной атомарной операцией.

## Промпт и ограничения

MentorPrompt задаёт русский язык, обращение на «ты», спокойную краткую поддержку,
запрет выдумывать воспоминания, ненавязчивые упражнения с учётом отказа, разделение
тона и дневника, JSON по контракту LlmClient и отсутствие заявления об уже
сохранённой записи. Текст находится в MentorPrompt.cpp. Качество выполнения этих
правил и полезность состава контекста пока не проверены настоящей моделью.
Отказ от упражнения учитывается по доступной истории; отдельной долговременной
настройки отказа пока нет. Отбор истории ограничен бюджетом, точных токенов нет.

Вызовы синхронные, конкурентная работа/смена чата во время вызова не поддерживается.
Нельзя вызывать сетевой клиент в потоке UI. ServerRuntime создаёт отдельную
связку для указанного chat_id. JSON и HTTP реализованы в [LlamaClient](LlamaClient.md) в infra;
при его локальном цикле событий повторный вход в сервисы нужно исключить.

TransactionRunner передаётся обязательной невладеющей ссылкой; все репозитории
связки должны использовать один исполнитель, для SQLite — одно соединение.
Проверка пакета фактов, дневник, профиль, Assistant и снятие действительного
ожидания выполняются одной транзакцией. Предметный отказ внутри callback
передаётся исключением ConversationRejection для отката, затем возвращается
обычным результатом. Технические исключения пробрасываются. Подтверждения
формируются при записи, но возвращаются лишь после успешной фиксации.

User записывается до LLM и остаётся при отказе/откате. После подтверждённого отката
исправным хранилищем возможен явный retryLastMessage без дублирования User,
дневника и фактов. После успешной записи последний Assistant исключает повтор.
При отказе отката SqliteDatabase закрывает соединение: сначала восстановить его
и перечитать историю. Автоматических повторов нет. Внешняя транзакция вокруг
sendMessage/retryLastMessage недопустима, так как охватит LLM и сохранение User.
Подробнее — [TransactionRunner](TransactionRunner.md).

offerEveningCheckIn использует отдельную транзакцию того же исполнителя: очистка
истёкшего ожидания, проверка даты/окна, сохранение даты выдачи, Assistant с текстом
опроса и новое ожидание. ID сообщения возвращается только после фиксации.
Ошибка любого этапа или commit восстанавливает прежние дату, историю и ожидание;
после подтверждённого отката публикацию можно явно повторить. Повтор в тот же день
не создаёт второе сообщение и не переносит ожидание при смене чата. При отсутствии
нового опроса транзакция может только снять истёкшее ожидание. LLM не вызывается.

Очистка истёкшего ожидания до/после LLM при обработке ответа выполняется отдельно
от транзакции ответа; истёкшее ожидание не восстанавливается при его откате.
В публикации очистка входит в её транзакцию и восстанавливается при сбое.
Атомарное сохранение не подтверждает доставку клиенту. ServerRuntime вызывает сервис
для отдельного chat_id и публикует события после commit; новые записи во время ожидания получают busy. Конкурентные вызовы сервиса не поддерживаются.

## Тесты

ConversationRejection содержит категорию Validation/Conflict/ContextBudgetExceeded,
по которой ServerRuntime выбирает код протокола без разбора русского текста причины.
Связка приложения проверяется дополнительно в tests/infra/src/ServerRuntimeTest.cpp.

Явный веб-поиск добавлен по решению 44: sendMessageWithSearch и
retryLastMessageWithSearch получают фразу отдельно от полного User.
Обязательная зависимость WebSearchProvider передаётся в конструктор, но обычные
sendMessage/retryLastMessage её не вызывают. Ошибки поиска возвращаются как
ExternalServiceError в ConversationResult, без LLM и записи ответа.
Источники возвращаются в searchSources и добавляются программой в текст Assistant;
они сохраняются той же транзакцией вместе с остальными изменениями ответа.
Режим/фраза отдельно не сохраняются: для повтора с поиском нужен явный
retryLastMessageWithSearch с фразой заново. Подробности —
[WebSearchProvider](WebSearchProvider.md).

`tests/core/src/ConversationServiceTest.cpp`: 20 сценариев с реальными сервисами,
FakeClock, FakeLlmClient и репозиториями в памяти. Проверяются состав контекста,
отсутствие повторного вопроса, сохранность заметки, подтверждение записи, выдача
и восстановление опроса, смена чата, отказ/другая тема/неясный ответ, полночь
до и во время LLM, явный повтор, ошибки бюджета и результата, копии состояния
и технический отказ дневника без ложного подтверждения. Это не проверка
семантического распознавания настоящей моделью. Команды — в [README](../../README.md).
Пять новых сценариев проверяют автоматическую память без дневника, общую ссылку
факта и дневника на User, смену версии в следующем контексте, запрет замены факта,
не вошедшего в бюджет, и отказ неоднозначного пакета до записи настроения.
Новый сценарий проверяет откат ошибки фиксации тестовым TransactionRunner и
повтор без второго User. `tests/infra/src/SqliteConversationTest.cpp` проверяет всю
связку с файловыми репозиториями: успех, сбой каждого из четырёх этапов, ошибку
commit, версии и теги после отката, повтор и отсутствие транзакции во время LLM.
Ещё один core-тест и три SQLite-теста проверяют публикацию: ошибки даты,
сообщения, ожидания и его очистки, ошибку commit, повтор после отката и открытия
файла, а также сохранение привязки к исходному чату при переключении.
Семь новых core-сценариев проверяют явный поиск, отсутствие старых триггеров,
передачу только фразы, источники, ошибки и бюджет до LLM, повтор без второго User.
Дополнительный SQLite-сценарий проверяет независимую запись во время поиска
и сохранение материалов в тексте Assistant после открытия файла заново.
Смена даты во время поиска не допускает запись ответа на уже истёкший опрос.

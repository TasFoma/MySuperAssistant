# TransactionRunner

Граница атомарной операции в core по решению 41. Заголовок —
`src/core/include/msa/core/TransactionRunner.h`, деструктор —
`src/core/src/TransactionRunner.cpp`. Только std::function, без Qt, SQL и IO.

`transaction` синхронно вызывает callback один раз и фиксирует нормальный возврат.
Любое исключение, в том числе ошибка фиксации, требует отката и пробрасывается.
Callback сообщает отказ исключением: возвращаемый статус не анализируется.
При невозможности отката дальнейшая работа с хранилищем запрещается реализацией.
Внешние вызовы LLM/сети внутри callback недопустимы.

## Реализации и зависимости

SqliteDatabase в infra реализует интерфейс напрямую существующим методом
`transaction`; вложенные SAVEPOINT остаются без изменений. Репозитории одного
атомарного действия должны получать один и тот же SqliteDatabase. Эта связь
задаётся при создании объектов, интерфейс не определяет владельца произвольного
репозитория автоматически. Приложения пока не собирают эту связку.

ConversationService получает TransactionRunner обязательной невладеющей ссылкой
через конструктор. Чат, дневник, профиль и состояние опроса должны использовать
этого же исполнителя. User сохраняется заранее; запрос LLM и проверка истечения
ожидания выполняются вне транзакции записи ответа. Внутри — проверка фактов,
необязательная запись дневника, профиль, Assistant и снятие действительного ожидания.
ConversationRejection используется как внутренний сигнал отката и перехватывается
после выхода из transaction; наружу возвращается обычный результат отказа.
Технические исключения пробрасываются. ConversationReply доступен после фиксации.

InMemoryTransactionRunner из `tests/core` делает снимки четырёх репозиториев,
при ошибке восстанавливает их вместе со счётчиками ID; вложенный успех остаётся
частью внешнего снимка. failNextCommit имитирует сбой после callback. Это тестовая
реализация, не запасной способ сохранения для приложения.

## Ограничения и проверки

Согласования конкурентных изменений и распределённых транзакций нет.
SQLite-реализация должна вызываться как внешняя граница записи ответа: если
вызывающий код уже держит внешнюю транзакцию, RELEASE внутреннего SAVEPOINT
ещё не означает окончательную фиксацию. Нельзя оборачивать sendMessage или
retryLastMessage в дополнительную транзакцию, охватывающую LLM.

offerEveningCheckIn использует отдельную транзакцию: очистка старого ожидания,
дата выдачи, сообщение и новое ожидание фиксируются вместе. ID возвращается после
успешной фиксации. При сбое прежнее состояние восстанавливается целиком.
После отказа отката закрытое соединение требует восстановления;
нельзя обещать безопасный повтор без перечитывания сохранённой истории.

Проверки: `tests/core/src/ConversationServiceTest.cpp` — откат при имитации ошибки
фиксации и повтор с одним User; `tests/infra/src/SqliteConversationTest.cpp` — фиксация
и повторное чтение, сбой каждого этапа записи, реальная ошибка финального RELEASE,
восстановление версий/тегов и возможность записи другим соединением во время LLM.
Механизм SQLite-вложенности и отказа отката проверяется в SqliteDatabaseTest.
Публикация проверена одним новым core-тестом и тремя SQLite-тестами: отказы всех
этапов, commit, восстановление прежнего ожидания, явный повтор и открытие файла заново.

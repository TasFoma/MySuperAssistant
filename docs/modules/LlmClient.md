# LlmClient

Контракт полного ответа LLM и общие проверки в `core` по решению 37.
Заголовок — `src/core/include/msa/core/LlmClient.h`, реализация —
`src/core/src/LlmClient.cpp`. Qt, JSON, HTTP и хранилище не используются.

## Точки входа

- `LlmRequest`: готовые сообщения из LlmContextBuilder и awaitingEveningCheckIn,
  который будущая связка чата устанавливает при ожидании ответа на опрос.
- `LlmClient::complete`: проверяет запрос, вызывает requestCompletion ровно один
  раз и проверяет полный результат. Неверный запрос не вызывает реализацию.
- `requestCompletion`: защищённая виртуальная точка для реализации в infra
  и FakeLlmClient в тестах. Возвращает полный ответ без потоковой выдачи.
- `LlmResponse`: reply, необязательные tone и moodRecording.
- `LlmFailure`: InvalidRequest, InvalidResponse или Unavailable с понятной причиной;
  LlmResult содержит либо полный ответ, либо ошибку.

Запрос начинается одним System, заканчивается текущим User, содержит минимум
два сообщения. В середине допустимы User/Assistant; строгого чередования нет.
Все тексты непустые после проверки пробелов Unicode, но исходные пробелы не
удаляются. Бюджет текста проверяется сборщиком до вызова.

Ответ проверяется целиком: непустой reply, оценки Negative/Neutral/Positive
либо отсутствие tone; предложение записи содержит допустимую оценку и причину
ExplicitRequest или EveningCheckInReply. Последняя причина допустима только
при awaitingEveningCheckIn=true. Неопределённый тон выражается nullopt.

## Предложение записи настроения

Тон относится к текущей реакции, из него не создаётся запись дневника.
Предложение записи независимо от тона: только распознанная явная просьба
или ответ на ожидаемый опрос. При смене темы модель должна вернуть отсутствие
предложения; сам флаг ожидания записи не требует.

После проверки complete заполняет moodRecording.note полным текстом последнего
User из запроса. Заметка от реализации заменяется исходником, включая пробелы,
переносы и подробности. Будущая связка передаст score и note в MoodService;
LlmClient сам не пишет ни дневник, ни историю чата.

Причина предложения остаётся результатом распознавания моделью: проверка типов
не доказывает наличие явной просьбы. Качество распознавания ещё не проверено.
Признак ожидания пока не связан с EveningCheckInService или хранилищем.

## Согласованный JSON модели для будущего infra

Это содержимое ответа модели, а не конверт HTTP и не протокол клиент ↔ сервер.
Будущий адаптер infra разбирает один полный JSON-объект без Markdown и другого
текста, проверяет поля и преобразует результат в LlmResponse:

```json
{
  "reply": "Текст ответа пользователю",
  "tone": "Positive",
  "mood_recording": {
    "score": "Positive",
    "reason": "ExplicitRequest"
  }
}
```

Все три поля обязательны. reply — непустая строка. tone — Negative, Neutral,
Positive или null. mood_recording — null либо объект с обязательными score
(Negative/Neutral/Positive) и reason (ExplicitRequest/EveningCheckInReply).
Неверные типы, неизвестные значения, отсутствующие или дополнительные поля —
ошибка формата. Поля note в JSON нет: исходник подставляет core. Для обычной
переписки mood_recording=null даже при определённом tone.

Адаптер должен донести awaitingEveningCheckIn до модели вместе с правилами
формата. Конкретный промпт ещё не выбран; в нём нужно сохранить правила ментора
из решения 32 и исключить запись каждого сообщения. JSON-разбор и HTTP пока
не реализованы и текущими тестами не проверяются.

## Ошибки и ограничения

Ошибки транспорта возвращаются как Unavailable, ошибки JSON и значений —
InvalidResponse. Частичного ответа и автоматических повторов нет. Пустая причина
ошибки заменяется общей понятной причиной. Реализация не должна возвращать
токены доступа и тела технических ответов сервера в пользовательской ошибке.
Ошибки памяти и дефекты реализации могут передаваться исключениями; будущая
граница приложения должна их обрабатывать.

Вызов синхронный: будущий сетевой клиент нельзя вызывать в потоке UI.
Управление выполнением, отменой и тайм-аутами пока отсутствует. Потоковая выдача
отложена до полного цикла чата. Нет реального LLM-клиента или вызовов приложений;
адрес, модель, точный бюджет токенов и резерв ответа здесь не выбираются.

## Тесты

`tests/core/FakeLlmClient.h/.cpp`: заданный результат и снимки запросов без сети.
`tests/core/LlmClientTest.cpp`: восемь сценариев передачи контекста без изменений,
отказа до вызова, независимости тона и дневника, исходной заметки, проверки
ожидания опроса, неверного полного ответа, ошибок без повторов и передачи
предложения в настоящий MoodService с хранилищем в памяти. Последний сценарий
показывает способ использования, а не готовую интеграцию чата.
Команды проверки — в [README](../../README.md).

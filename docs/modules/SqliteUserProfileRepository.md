# SqliteUserProfileRepository

SQLite-реализация `core::UserProfileRepository` по решениям 27, 36, 39 и 40.
Хранит полный профиль: постоянные ID, порядок фактов, тексты, упорядоченные теги
с повторами, alwaysInclude, источники и обе ссылки версий. API —
`src/infra/include/msa/infra/SqliteUserProfileRepository.h`, реализация —
`src/infra/src/SqliteUserProfileRepository.cpp`.

## Схема и точки входа

Вызывающий код открывает SqliteDatabase со всем списком `sqliteMigrations()`,
затем передаёт владельца в конструктор репозитория. Владелец живёт дольше
репозитория; все операции выполняются в его потоке при живом QCoreApplication.
Приложения пока не создают эти объекты.

Миграция 3 добавляет `profile_facts` и `profile_fact_tags`. ID фактов задаёт
UserProfileService; репозиторий их не перенумеровывает. Отдельные позиции
сохраняют порядок фактов и тегов независимо от ID и текста. Тексты передаются
подготовленными запросами, без нормализации, обрезки или ограничения длины.
Нулевой символ, Unicode, переводы строк и повторы сохраняются.

Источник содержит пару ID сообщения и чата. Миграция добавляет уникальный индекс
на эту пару в chat_messages и составной внешний ключ: сообщение должно
существовать именно в указанном чате. Отсутствие источника и отсутствие ID
дневника различаются SQL NULL. Роль User обеспечивает ConversationService.
С версии 7 source_mood — внешний ключ на mood_entries из
[SqliteMoodRepository](SqliteMoodRepository.md). Обновление сохраняет все факты,
теги и ссылки версий, но отклоняется с полным откатом при отсутствующем дневнике
в старой ненулевой ссылке. Отсутствие source_mood по-прежнему разрешено.

`load` возвращает независимую копию всех версий в сохранённом порядке, изначально
профиль пуст. Факты и теги читаются в одной транзакции, чтобы получить общий снимок.
Для присоединения тегов используется таблица соответствия ID и позиции в результате.

`save` заменяет профиль целиком в транзакции: удаляет прежний снимок с каскадным
удалением тегов, затем вставляет факты и теги из нового. Пустой профиль очищает
хранилище по явному вызову save; автоматической очистки нет. Положительные
уникальные ID и ссылки версий проверяет схема. Отложенные внешние ключи версий
позволяют вставлять старую и новую записи с взаимными ссылками в любом порядке.
Проверки содержимого и правил исправлений остаются в UserProfileService.

## Атомарность и ограничения

Ошибка запроса или окончательной фиксации откатывает весь save, включая прежние
теги и отметки версий. Технические ошибки передаются std::runtime_error;
ошибки чтения не маскируются пустым профилем. При внешней транзакции save использует
вложенный SAVEPOINT, успех остаётся частью внешней операции. Отложенные ссылки
проверяются при фиксации самой внешней транзакции.

Весь профиль загружается и заменяется целиком. Конкурентные изменения снимков
могут приводить к потерянным обновлениям; сервисы пока используются последовательно.
ConversationService объединяет профиль, дневник, Assistant и снятие ожидания через
TransactionRunner; все репозитории должны использовать одного владельца базы.
Ручной интерфейс редактирования/удаления и автоматические теги не добавлены.
Импорта старой базы нет.

## Тесты

`tests/infra/SqliteUserProfileRepositoryTest.cpp`: 10 файловых тестов.
Проверяются переход с версии 2 без потери чатов, повторное открытие, точные ID,
порядок, Unicode и NUL, длинный текст, повторы тегов, приоритет, источники с/без
дневника, ссылки версий, замена и пустой снимок, независимые копии, откат при
позднем сбое тега/повторном ID/неверных ссылках, участие во внешней транзакции,
ошибки чтения, более 30 фактов, ручные повторы. Связка с UserProfileService
проверяет постоянные ID после открытия заново, исправление и пропуск автоматического
повтора; UserProfileFactSelector исключает старую версию из контекста.
Команды — в [README](../../README.md).

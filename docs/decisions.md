# Журнал решений

Здесь записаны архитектурные решения проекта: что решили, почему и что отбросили.
Новое решение добавляется в конец; старое не удаляется, а помечается «Заменено решением N».

Статусы:
- **Принято** — следовать.
- **Предложено** — рабочий вариант, следовать, пока не изменено.
- **Открыто** — решения нет; агент не выбирает сам, а спрашивает пользователя.

---

## 1. Мобильный клиент на C++/Qt вместо Flutter

- **Дата:** 2026-10-26
- **Статус:** Принято
- **Решение:** телефон пишется на C++/Qt (Qt for Android), а не на Flutter, как в старом проекте.
- **Почему:** один язык во всём проекте; общий `core`, общие модели и QML-компоненты в `ui/common`
  для ПК и телефона.
- **Отброшено:** оставить Flutter — пришлось бы дублировать логику и протокол на Dart.
- **Цена решения:** уведомления и распознавание речи на Android потребуют JNI-обёрток.

## 2. Три приложения и слои

- **Дата:** 2026-10-26
- **Статус:** Принято
- **Решение:** приложения `apps/server` («мозг» без окна), `apps/desktop`, `apps/mobile`.
  Слои `core` → `infra` → `ui/common`, `ui/desktop`, `ui/mobile`, подробности в `.clinerules`.
- **Почему:** идея «сервер + тонкие клиенты» из старого проекта работает; данные и логика в одном месте,
  телефон и ПК видят одно и то же.
- **Отброшено:** каждое устройство со своей базой и синхронизацией — сложнее и пока не нужно.

## 3. Протокол клиент ↔ сервер

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** как в старом проекте: TCP, порт 8765, JSON-объекты по одному на строку.
  Первое сообщение клиента — `auth` с токеном. Шифрование транспорта обеспечивает Tailscale.
- **Почему:** протокол уже работает и описан в `docs/old-project-overview.md`; менять транспорт
  сейчас незачем.
- **Отброшено:** WebSocket, HTTP REST, gRPC.
- **Пересмотреть, если:** понадобится клиент в браузере или доступ без Tailscale.

## 4. LLM

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** внешний llama-server с OpenAI-совместимым API (`/v1/chat/completions`).
  `core` знает только интерфейс LLM-клиента, HTTP-реализация — в `infra`.
- **Почему:** модель можно менять и запускать на другой машине, не трогая логику.

## 5. Хранение данных

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** SQLite на сервере через Qt Sql в `infra`. В `core` — интерфейсы репозиториев.
  На клиентах — только кэш последнего снапшота.
- **Почему:** одна база — нет конфликтов синхронизации.
- **Отброшено:** синглтон `DatabaseManager` из старого проекта. База создаётся в `apps/server`
  и передаётся в репозитории через конструктор.
- **Пересмотреть, если:** телефону понадобится полноценная работа без связи с сервером.

## 6. Без прямого запасного пути телефона к llama-server

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** на первом этапе телефон общается только с сервером. Прямой запрос к llama-server
  из старого `llama_service.dart` не переносится.
- **Почему:** один путь чата — проще логика и отладка, история всегда сохраняется на сервере.

## 7. Личные значения не в коде

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** IP-адреса, токены, порты, адрес llama-server — только в файле настроек
  или настройках приложения. В код и в git не попадают; в репозитории — пример с заглушками.
- **Почему:** в старом проекте они прошиты в `app_settings.dart` и `sync_service.dart`.

## 8. Внешние сервисы навигации и погоды

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** Nominatim (геокодинг), OSRM (маршруты), open-meteo (погода) — как в старом проекте,
  каждый за интерфейсом из `core`, реализации в `infra`.

## 9. Что не переносится

- **Дата:** 2026-10-26
- **Статус:** Принято
- **Решение:** `server/server.cpp` (тестовый эхо-сервер на порту 12000) и первая версия `qt_client`
  не переносятся. Источник для переноса — `qt_client_clean` и `android_client`.

## 10. Зависимости и тесты

- **Дата:** 2026-10-27
- **Статус:** Принято
- **Решение:** тесты на GoogleTest, подключается через CMake `FetchContent` с закреплённой версией.
  Пакетный менеджер пока не используем: Qt ставится установщиком и покрывает сеть, SQL, JSON и мультимедиа.
- **Почему:** единственная внешняя зависимость — GoogleTest; Conan ради неё усложнил бы сборку,
  особенно под Android.
- **Версия:** GoogleTest v1.18.0 (закреплена в `cmake/Dependencies.cmake`).
- **Пересмотреть, если:** появится несколько внешних библиотек — тогда Conan, как на работе.

## 11. PCRE2 в core для разбора команд

- **Дата:** 2026-10-27
- **Статус:** Предложено
- **Решение:** PCRE2 в core — исключение из правила "только stdlib": чистая вычислительная библиотека без IO, совпадает с движком QRegularExpression.
- **Версия:** PCRE2 10.47 (тег `pcre2-10.47`), подключается через `FetchContent` в `cmake/Pcre2.cmake`. Только 8-битная библиотека, с UTF и Unicode-свойствами.
- **Почему:** `std::regex` не поддерживает Unicode-свойства, а `std::wregex` на Windows работает с 16-битными символами. Поведение разбора переносится из старого Qt-кода без изменений.
- **Отброшено:** `std::wregex` с ручной эмуляцией `\w`, `\b` и регистра — хрупко.
- **Пересмотреть, если:** PCRE2 начнёт мешать сборке под Android.

## 12. Общая настройка Qt в корне CMake

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** один вызов `find_package(Qt6 6.10 REQUIRED COMPONENTS Gui Quick)` в корневом
  `CMakeLists.txt`, до подключения подкаталогов и развилки Android/desktop. Сразу после него —
  `qt_standard_project_setup()`. В подкаталогах поиск Qt не дублируется.
- **Почему:** обеим клиентским веткам нужен Quick; цели Qt должны быть видны при финализации
  приложений, чтобы CMake корректно обходил зависимости UI-библиотек.
- **Ограничение:** `core` и `apps/server` с Qt не линкуются.

## 13. Напоминание без времени при переходе через полночь

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** если время не указано, напоминание назначается через час с переходом даты
  на следующий день, когда требуется. Текущее поведение нового `CommandParser` закреплено тестом.
- **Почему:** старый парсер прибавлял час только ко времени и после 23:00 оставлял прежнюю дату,
  получая момент в прошлом. Пользователь одобрил исправленное поведение.

## 14. Типы планировщика в core

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** сохранить поля задач, событий, напоминаний, привычек и записей прогресса
  из старого планировщика. Профиль — список фактов в порядке добавления без маркеров оформления.
  Прогресс привычки вычисляется из записей, а не хранится в самой привычке.
- **Типы:** приоритет задачи — `Low`, `Normal`, `High`; повтор события — `None`, `Daily`,
  `Weekly`, `Monthly`; период привычки — `Day`, `Week`. Все перечисления — `enum class`.
- **Напоминания:** отдельные `TimedReminder`, `RecurringReminder`, `PlaceReminder`,
  объединённые в `Reminder` через `std::variant`.
- **Координаты:** `std::optional<GeoCoordinates>`; нулевая широта и долгота допустимы.
  Старое обозначение отсутствующих координат нулём не переносится: оно исключало места на экваторе.
- **Время:** пока местное время сервера через `std::chrono`; необязательные срок задачи
  и время события — через `std::optional`. Время события — минуты от полуночи,
  моменты создания и срабатывания — с точностью до секунд.
- **Почему:** сохранить возможности старого планировщика без Qt и SQL в предметной области,
  явно различать отсутствие значения и допустимое нулевое значение.
- **Граница шага:** только структуры данных. Проверки входных данных, ограничение профиля
  последними 30 фактами, расчёт прогресса и правила срабатывания относятся к следующим шагам логики.
  Ограничение последними 30 фактами заменено решением 27.

## 15. Обработка ошибок репозиториев

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** технические ошибки хранилища передаются исключениями без Qt-типов.
  Реализации в `infra` преобразуют ошибки Qt Sql в такие исключения.
- **Обычные результаты:** отсутствие записи при поиске — `std::optional`, отсутствие
  элементов списка — пустой `std::vector`. Эти ситуации не считаются техническими ошибками.
- **Проверка ввода:** неверные пользовательские данные возвращаются отдельным результатом
  проверки с причиной для интерфейса, а не исключением технической ошибки.
- **Граница обработки:** исключения перехватываются на границе операции приложения;
  сервер возвращает клиенту ошибку и продолжает работу. В асинхронных обработчиках Qt
  исключения перехватываются внутри обработчика и не выходят в цикл событий.
- **Почему:** сохраняем C++20 и текущие зависимости; для этого решения не нужны C++23
  с `std::expected` или дополнительная библиотека `tl::expected`.

## 16. Ошибки регулярных выражений и длина результатов парсера

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** ошибка компиляции шаблона PCRE2 вызывает исключение в конструкторе;
  при поиске только `PCRE2_ERROR_NOMATCH` означает отсутствие совпадения,
  остальные ошибки вызывают исключение.
- **Проверка текста:** минимум три кодовые точки для заголовков во всех обработчиках,
  а также факта памяти и места маршрута. Короткий распознанный результат — `NoCommand`.
- **Почему:** ошибки движка не должны маскироваться под неизвестную команду;
  неполная проверка длины в старом парсере не сохраняется.
- **Напоминания в прошлом:** парсер оставляет явно указанную дату; предметное правило
  требуется отдельно согласовать на этапе 1.
- **Qt:** необходимость Qt для конфигурации всего проекта ожидаема и сохраняется.

## 17. Создание напоминаний в прошлом

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** при создании напоминания с моментом в прошлом отклонять операцию
  с понятной причиной и просьбой указать другое время. Запись не сохраняется.
- **Граница:** проверка относится к логике планировщика; парсер дату не исправляет.
  Поведение уже сохранённых напоминаний, просроченных во время остановки сервера,
  этим решением не определяется.
- **Почему:** пользователь должен явно выбрать новое время.

## 18. Просроченные напоминания и интервалы

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** однократные напоминания, просроченные во время остановки сервера,
  после запуска не показывать.
- **Повторяющиеся:** при пропуске нескольких интервалов показать один раз,
  следующий запуск назначить как текущее время плюс интервал.
- **Проверка ввода:** нулевой и отрицательный интервал отклонять с понятной причиной;
  старую молчаливую замену на 60 минут не переносить.
- **Уточнение:** завершение пропущенного напоминания определено решением 19.

## 19. Статус однократного напоминания

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** вместо `fired` используется `ReminderStatus`: `Pending`, `Fired`, `Missed`.
  При запуске просроченные однократные напоминания становятся `Missed` без уведомления.
  Повторяющиеся срабатывают один раз и переносятся на сейчас плюс интервал.
- **Почему:** различать показанные и пропущенные напоминания.

## 20. Ежемесячные события в коротких месяцах

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** если исходного числа нет в месяце, событие происходит в последний
  день месяца. Исходная дата не меняется: 31 января → 28/29 февраля → 31 марта.
- **Почему:** пользователь выбрал перенос вместо пропуска короткого месяца.
- **Граница:** годового повторения в модели нет; для события от 29 февраля
  с ежемесячным повторением действует то же правило числа месяца.

## 21. Отметки и прогресс привычек

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** цель и отметка — положительные конечные числа; ноль, отрицательные
  значения, NaN и бесконечность отклоняются с причиной без сохранения.
- **Период:** отметки создаются за местный сегодняшний день сервера. Дневной прогресс —
  сумма за сегодня, недельный — с понедельника по сегодня включительно.
  Будущие записи исключаются; старый запрос без верхней границы не переносится.
- **Цель:** сумма может превышать цель и не обрезается.
- **Почему:** пользователь одобрил явные проверки и ограничение текущим днём.

## 22. Ежедневное приветствие по времени суток

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** один раз за местный календарный день при первой проверке, включая
  ночь. 00:00–07:59 — «Доброй ночи», 08:00–11:59 — «Доброе утро»,
  12:00–17:59 — «Добрый день», 18:00–23:59 — «Добрый вечер».
- **Состав:** дата, события на сегодня и максимум пять незавершённых задач.
  Сначала высокий приоритет, затем ближайший срок; без срока — после датированных
  внутри приоритета. При равенстве — по ID для определённого порядка.
- **Хранение:** отдельный `GreetingRepository` в core, реализация в памяти для тестов,
  SQLite-реализация на этапе 3. Дата сохраняется после формирования текста до возврата.
- **Почему:** подходящее времени суток обращение и отсутствие повторов после перезапуска
  при использовании одного сохранённого состояния.

## 23. Операции с задачами

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** при создании и изменении заголовок содержит минимум одну кодовую точку;
  необязательная дата должна быть корректной, приоритет — Low, Normal или High.
  Прошедший срок разрешён: задача может быть просроченной.
- **Сортировка:** сначала незавершённые, внутри каждой группы — высокий приоритет,
  ближайший срок, без срока после датированных внутри приоритета; при равенстве — ID.
- **Поведение:** создание берёт время из Clock и задаёт done=false; изменение полей
  сохраняет время создания и статус. Завершённость можно установить и снять.
- **Почему:** пользователь подтвердил проверки и определённый порядок, согласованный
  с приветствием. Минимум в три символа из парсера на сервис задач не распространяется.

## 24. Создание и изменение событий

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** заголовок содержит минимум одну кодовую точку; дата обязательна
  и корректна, события в прошлом разрешены. Время необязательно, при наличии —
  от 00:00 до 23:59. Описание необязательно. Повтор — None, Daily, Weekly или Monthly.
- **Изменение:** заменяет поля всей серии с сохранением ID; редактирования отдельных
  вхождений нет. Чтение календаря остаётся в CalendarService.
- **Почему:** пользователь подтвердил явную проверку ввода вместо её отсутствия
  в старом коде и сохранение модели одной записи на всю серию.

## 25. Геонапоминания

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** однократное срабатывание при расстоянии строго меньше 200 м.
  Расстояние вычисляется по сфере (формула гаверсинусов, радиус 6 371 000 м),
  с корректной обработкой перехода долготы через ±180°.
- **Проверки:** название и место содержат минимум одну кодовую точку.
  Координаты необязательны; без них запись хранится, но не срабатывает.
  Числа конечны, широта в пределах −90…90, долгота −180…180; нули допустимы.
- **Срабатывание:** Pending становится Fired до возврата исходной записи для
  уведомления; повторной выдачи нет. Получение позиции и доставка — вне core.
- **Почему:** пользователь подтвердил сохранение радиуса и исправление приближённого
  расчёта старого кода; отсутствие координат уже выражено через optional (решение 14).

## 26. Предупреждения о событиях

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** событие со временем выдаётся при первой проверке, когда до начала
  строго больше 0 и не больше 60 минут, включая последнюю минуту и события
  следующего дня после полуночи. После начала пропущенные предупреждения не выдаются.
- **Без времени:** предупреждать накануне и в день события при первой проверке
  с 08:00 местного времени; поздний запуск выдаёт предупреждение в этот день.
  Повторы обрабатываются CalendarService по тем же правилам.
- **Отметки:** отдельный EventWarningRepository; ключ — ID + дата вхождения + вид
  (перед началом, накануне, сегодня). Изменение времени в этот день не сбрасывает
  отметку перед началом. Отметка сохраняется до возврата предупреждения.
- **Хранение:** сейчас реализация в памяти для тестов; SQLite — этап 3, для сохранения
  защиты от повторов после перезапуска. Получение и доставка предупреждений — вне сервиса.
- **Почему:** пользователь расширил окно до часа и добавил два предупреждения для
  событий без времени; подтвердил 08:00 и поведение при позднем запуске.

## 27. Полная память профиля и ограниченный контекст LLM

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** хранить все факты профиля в порядке добавления без автоматического
  удаления старых. Лимит последних 30 фактов из плана и решения 14 отменён:
  давность факта не означает, что он перестал быть важным.
- **Ввод:** обрезать пробельные символы Unicode по краям; пустой результат отклонять
  с понятной причиной без сохранения. Многострочный текст — один факт, внутренние
  пробелы и переносы сохраняются. Повторы сохраняются, маркеры оформления не добавляются.
- **Контекст:** ограничивать объём памяти, передаваемой LLM, а не хранимые данные.
  Подбор по теме разговора и доступному объёму контекста относится к этапу 2;
  конкретный алгоритм ещё не выбран. Возможные сводки не заменяют исходные факты.
- **Теги:** пользователь предложил подумать о тегах для поиска по фактам позже.
  Формат тегов, назначение и поиск пока не согласованы и не реализуются в этом шаге.
- **Почему:** сохранять информацию независимо от ограничений контекста модели.

## 28. Сводка дня и граница с контекстом чата

- **Дата:** 2026-11-06

- **Решение:** на этапе 1 `DailyContextService` формирует текст с местными датой
  и временем сервера, событиями сегодня с учётом повторов, максимум пятью открытыми

  памяти. Полезность состава и отбора контекста оценим после подключения чата.

## 29. Вечерний опрос настроения

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** предлагать опрос при первой проверке с 20:00 включительно до конца
  местного календарного дня сервера. Старое окно 20:00–20:59 расширено, чтобы

## 31. Дневник настроения и анализ через LLM

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Анализ:** словарный анализ тона не переносится. Анализ через LLM подключается
  вместе с чатом; оценку для текущей реакции предполагается получать в том же ответе,
  без отдельного запроса. Формат ответа и интеграция пока не реализованы.
- **Запись:** в дневник попадают явные отметки пользователя: ответ на вечерний опрос
  или просьба записать настроение. Каждое обычное сообщение автоматически не записывается.
  Оценка — Negative, Neutral или Positive; все три допустимы для явной записи.
- **Данные:** MoodService сохраняет оценку, местное время из Clock с точностью
  до секунд и полный текст заметки без обрезки или изменения пробелов. Заметка
  может быть пустой; повторные явные записи сохраняются отдельно.
- **История:** по умолчанию 14 календарных дней, включая сегодня: с 00:00 первого
  дня до текущего момента включительно. Например, 6 ноября — с 00:00 24 октября.
  Будущие записи исключаются; порядок — время по возрастанию, затем ID.
  Неположительное число дней и неизвестная оценка отклоняются с причиной.
- **Сохранность:** период ограничивает только выборку; старые записи не удаляются.
  Можно запросить больший период. Профиль также сохраняет все факты (решение 27).
  Пользователь ожидает долговременную память о биографии и важных жизненных событиях;
  автоматическое выделение этих фактов из чата и связь с дневником ещё не выбраны
  и не реализованы. Нельзя полагаться на автоматический перенос в профиль.
- **Граница:** сейчас дневник, интерфейс MoodRepository и реализация в памяти для
  тестов. SQLite — этап 3; распознавание ответа на опрос, вызовы из чата, анализ LLM
  и поддерживающие подсказки — следующие шаги этапа 2.
- **Почему:** пользователь выбрал анализ LLM, подтвердил явные записи и календарный
  период; полный текст и отсутствие очистки сохраняют важные события независимо
  от периода просмотра и будущего отбора контекста LLM.

## 32. Поддержка ментора в обычном ответе LLM

- **Почему:** пользователь согласовал поддержку по контексту разговора вместо
  случайной заготовки и отсутствие дополнительного запроса к модели.

## 33. Чаты, полный текст сообщений и восстановление выбора

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** сохранить несколько чатов и выбор текущего. При запуске восстановить
  сохранённый чат, если он существует; иначе выбрать чат с максимальным ID,
  а при пустом хранилище создать новый. Название нового чата —
  «Чат от ДД.ММ.ГГГГ ЧЧ:ММ», дата и время берутся из Clock в местной шкале сервера.
- **Переключение:** несуществующий чат отклоняется с понятной причиной;
  текущий выбор не меняется. Новый выбор сохраняется до смены состояния сервиса.
- **Сообщения:** роли User и Assistant; неизвестная роль, пустой текст или текст
  только из пробельных символов Unicode отклоняются без записи. Остальной текст
  сохраняется полностью, включая исходные пробелы и переносы; время берётся из Clock.
  Повторные сообщения сохраняются отдельно, автоматического удаления нет.
- **Порядок:** список чатов по ID от новых к старым, сообщения текущего чата
  по ID от старых к новым; перевод часов не меняет порядок переписки.
- **Граница:** ChatService, типы Chat/ChatMessage, интерфейс ChatRepository
  и реализация в памяти для тестов. SQLite — этап 3; UI и вызовы из приложений
  пока отсутствуют. Сборка контекста LLM — следующий шаг, лимиты 40 сообщений
  и 4000 символов старого ChatManager пока не перенесены и не согласованы.
- **Почему:** пользователь подтвердил восстановление выбора и полную историю,
  проверки переключения и ввода вместо молчаливого принятия неверных данных.

# Журнал решений

Здесь записаны архитектурные решения проекта: что решили, почему и что отбросили.
Новое решение добавляется в конец; старое не удаляется, а помечается «Заменено решением N».

Статусы:
- **Принято** — следовать.
- **Предложено** — рабочий вариант, следовать, пока не изменено.
- **Открыто** — решения нет; агент не выбирает сам, а спрашивает пользователя.

---

## 1. Мобильный клиент на C++/Qt вместо Flutter

- **Дата:** 2026-10-26
- **Статус:** Принято
- **Решение:** телефон пишется на C++/Qt (Qt for Android), а не на Flutter, как в старом проекте.
- **Почему:** один язык во всём проекте; общий `core`, общие модели и QML-компоненты в `ui/common`
  для ПК и телефона.
- **Отброшено:** оставить Flutter — пришлось бы дублировать логику и протокол на Dart.
- **Цена решения:** уведомления и распознавание речи на Android потребуют JNI-обёрток.

## 2. Три приложения и слои

- **Дата:** 2026-10-26
- **Статус:** Принято
- **Решение:** приложения `apps/server` («мозг» без окна), `apps/desktop`, `apps/mobile`.
  Слои `core` → `infra` → `ui/common`, `ui/desktop`, `ui/mobile`, подробности в `.clinerules`.
- **Почему:** идея «сервер + тонкие клиенты» из старого проекта работает; данные и логика в одном месте,
  телефон и ПК видят одно и то же.
- **Отброшено:** каждое устройство со своей базой и синхронизацией — сложнее и пока не нужно.

## 3. Протокол клиент ↔ сервер

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** как в старом проекте: TCP, порт 8765, JSON-объекты по одному на строку.
  Первое сообщение клиента — `auth` с токеном. Шифрование транспорта обеспечивает Tailscale.
- **Почему:** протокол уже работает и описан в `docs/old-project-overview.md`; менять транспорт
  сейчас незачем.
- **Отброшено:** WebSocket, HTTP REST, gRPC.
- **Пересмотреть, если:** понадобится клиент в браузере или доступ без Tailscale.

## 4. LLM

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** внешний llama-server с OpenAI-совместимым API (`/v1/chat/completions`).
  `core` знает только интерфейс LLM-клиента, HTTP-реализация — в `infra`.
- **Почему:** модель можно менять и запускать на другой машине, не трогая логику.

## 5. Хранение данных

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** SQLite на сервере через Qt Sql в `infra`. В `core` — интерфейсы репозиториев.
  На клиентах — только кэш последнего снапшота.
- **Почему:** одна база — нет конфликтов синхронизации.
- **Отброшено:** синглтон `DatabaseManager` из старого проекта. База создаётся в `apps/server`
  и передаётся в репозитории через конструктор.
- **Пересмотреть, если:** телефону понадобится полноценная работа без связи с сервером.

## 6. Без прямого запасного пути телефона к llama-server

- **Дата:** 2026-10-26
- **Статус:** Предложено
- **Решение:** на первом этапе телефон общается только с сервером. Прямой запрос к llama-server
  из старого `llama_service.dart` не переносится.
- **Почему:** один путь чата — проще логика и отладка, история всегда сохраняется на сервере.

## 7. Личные значения не в коде

- **Почему:** в старом проекте они прошиты в `app_settings.dart` и `sync_service.dart`.

## 10. Зависимости и тесты

- **Дата:** 2026-10-27
- **Статус:** Принято
- **Решение:** тесты на GoogleTest, подключается через CMake `FetchContent` с закреплённой версией.
  Пакетный менеджер пока не используем: Qt ставится установщиком и покрывает сеть, SQL, JSON и мультимедиа.
- **Почему:** единственная внешняя зависимость — GoogleTest; Conan ради неё усложнил бы сборку,
  особенно под Android.
- **Версия:** GoogleTest v1.18.0 (закреплена в `cmake/Dependencies.cmake`).
- **Пересмотреть, если:** появится несколько внешних библиотек — тогда Conan, как на работе.

## 11. PCRE2 в core для разбора команд

- **Дата:** 2026-10-27
- **Статус:** Предложено
- **Решение:** PCRE2 в core — исключение из правила "только stdlib": чистая вычислительная библиотека без IO, совпадает с движком QRegularExpression.
- **Версия:** PCRE2 10.47 (тег `pcre2-10.47`), подключается через `FetchContent` в `cmake/Pcre2.cmake`. Только 8-битная библиотека, с UTF и Unicode-свойствами.
- **Почему:** `std::regex` не поддерживает Unicode-свойства, а `std::wregex` на Windows работает с 16-битными символами. Поведение разбора переносится из старого Qt-кода без изменений.
- **Отброшено:** `std::wregex` с ручной эмуляцией `\w`, `\b` и регистра — хрупко.
- **Пересмотреть, если:** PCRE2 начнёт мешать сборке под Android.

## 12. Общая настройка Qt в корне CMake

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** один вызов `find_package(Qt6 6.10 REQUIRED COMPONENTS Gui Quick)` в корневом
  `CMakeLists.txt`, до подключения подкаталогов и развилки Android/desktop. Сразу после него —
  `qt_standard_project_setup()`. В подкаталогах поиск Qt не дублируется.
- **Почему:** обеим клиентским веткам нужен Quick; цели Qt должны быть видны при финализации
  приложений, чтобы CMake корректно обходил зависимости UI-библиотек.
- **Ограничение:** `core` с Qt не линкуется. Ограничение для `apps/server`
  заменено решением 40: сервер получает Qt Sql транзитивно через infra.

## 13. Напоминание без времени при переходе через полночь

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** если время не указано, напоминание назначается через час с переходом даты

## 14. Типы планировщика в core

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** сохранить поля задач, событий, напоминаний, привычек и записей прогресса
  из старого планировщика. Профиль — список фактов в порядке добавления без маркеров оформления.
  Прогресс привычки вычисляется из записей, а не хранится в самой привычке.
- **Типы:** приоритет задачи — `Low`, `Normal`, `High`; повтор события — `None`, `Daily`,
  `Weekly`, `Monthly`; период привычки — `Day`, `Week`. Все перечисления — `enum class`.
- **Напоминания:** отдельные `TimedReminder`, `RecurringReminder`, `PlaceReminder`,
  объединённые в `Reminder` через `std::variant`.
- **Координаты:** `std::optional<GeoCoordinates>`; нулевая широта и долгота допустимы.
  Старое обозначение отсутствующих координат нулём не переносится: оно исключало места на экваторе.
- **Время:** пока местное время сервера через `std::chrono`; необязательные срок задачи
  и время события — через `std::optional`. Время события — минуты от полуночи,
  моменты создания и срабатывания — с точностью до секунд.
- **Почему:** сохранить возможности старого планировщика без Qt и SQL в предметной области,
  явно различать отсутствие значения и допустимое нулевое значение.
- **Граница шага:** только структуры данных. Проверки входных данных, ограничение профиля
  последними 30 фактами, расчёт прогресса и правила срабатывания относятся к следующим шагам логики.
  Ограничение последними 30 фактами заменено решением 27.

## 15. Обработка ошибок репозиториев

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** технические ошибки хранилища передаются исключениями без Qt-типов.
  Реализации в `infra` преобразуют ошибки Qt Sql в такие исключения.
- **Обычные результаты:** отсутствие записи при поиске — `std::optional`, отсутствие
  элементов списка — пустой `std::vector`. Эти ситуации не считаются техническими ошибками.
- **Проверка ввода:** неверные пользовательские данные возвращаются отдельным результатом
  проверки с причиной для интерфейса, а не исключением технической ошибки.
- **Граница обработки:** исключения перехватываются на границе операции приложения;
  сервер возвращает клиенту ошибку и продолжает работу. В асинхронных обработчиках Qt
  исключения перехватываются внутри обработчика и не выходят в цикл событий.
- **Почему:** сохраняем C++20 и текущие зависимости; для этого решения не нужны C++23
  с `std::expected` или дополнительная библиотека `tl::expected`.

## 16. Ошибки регулярных выражений и длина результатов парсера

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** ошибка компиляции шаблона PCRE2 вызывает исключение в конструкторе;
  при поиске только `PCRE2_ERROR_NOMATCH` означает отсутствие совпадения,
  остальные ошибки вызывают исключение.
- **Проверка текста:** минимум три кодовые точки для заголовков во всех обработчиках,
  а также факта памяти и места маршрута. Короткий распознанный результат — `NoCommand`.
- **Почему:** ошибки движка не должны маскироваться под неизвестную команду;
  неполная проверка длины в старом парсере не сохраняется.
- **Напоминания в прошлом:** парсер оставляет явно указанную дату; предметное правило
  требуется отдельно согласовать на этапе 1.
- **Qt:** необходимость Qt для конфигурации всего проекта ожидаема и сохраняется.

## 17. Создание напоминаний в прошлом

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** при создании напоминания с моментом в прошлом отклонять операцию
  с понятной причиной и просьбой указать другое время. Запись не сохраняется.
- **Граница:** проверка относится к логике планировщика; парсер дату не исправляет.
  Поведение уже сохранённых напоминаний, просроченных во время остановки сервера,
  этим решением не определяется.
- **Почему:** пользователь должен явно выбрать новое время.

## 18. Просроченные напоминания и интервалы

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** однократные напоминания, просроченные во время остановки сервера,
  после запуска не показывать.
- **Повторяющиеся:** при пропуске нескольких интервалов показать один раз,
  следующий запуск назначить как текущее время плюс интервал.
- **Проверка ввода:** нулевой и отрицательный интервал отклонять с понятной причиной;
  старую молчаливую замену на 60 минут не переносить.
- **Уточнение:** завершение пропущенного напоминания определено решением 19.

## 19. Статус однократного напоминания

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** вместо `fired` используется `ReminderStatus`: `Pending`, `Fired`, `Missed`.
  При запуске просроченные однократные напоминания становятся `Missed` без уведомления.
  Повторяющиеся срабатывают один раз и переносятся на сейчас плюс интервал.
- **Почему:** различать показанные и пропущенные напоминания.

## 20. Ежемесячные события в коротких месяцах

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** если исходного числа нет в месяце, событие происходит в последний
  день месяца. Исходная дата не меняется: 31 января → 28/29 февраля → 31 марта.
- **Почему:** пользователь выбрал перенос вместо пропуска короткого месяца.
- **Граница:** годового повторения в модели нет; для события от 29 февраля
  с ежемесячным повторением действует то же правило числа месяца.

## 21. Отметки и прогресс привычек

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** цель и отметка — положительные конечные числа; ноль, отрицательные
  значения, NaN и бесконечность отклоняются с причиной без сохранения.
- **Период:** отметки создаются за местный сегодняшний день сервера. Дневной прогресс —
  сумма за сегодня, недельный — с понедельника по сегодня включительно.
  Будущие записи исключаются; старый запрос без верхней границы не переносится.
- **Цель:** сумма может превышать цель и не обрезается.
- **Почему:** пользователь одобрил явные проверки и ограничение текущим днём.

## 22. Ежедневное приветствие по времени суток

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** один раз за местный календарный день при первой проверке, включая
  ночь. 00:00–07:59 — «Доброй ночи», 08:00–11:59 — «Доброе утро»,
  12:00–17:59 — «Добрый день», 18:00–23:59 — «Добрый вечер».
- **Состав:** дата, события на сегодня и максимум пять незавершённых задач.
  Сначала высокий приоритет, затем ближайший срок; без срока — после датированных
  внутри приоритета. При равенстве — по ID для определённого порядка.
- **Хранение:** отдельный `GreetingRepository` в core, реализация в памяти для тестов,
  SQLite-реализация на этапе 3. Дата сохраняется после формирования текста до возврата.
- **Почему:** подходящее времени суток обращение и отсутствие повторов после перезапуска
  при использовании одного сохранённого состояния.

## 23. Операции с задачами

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** при создании и изменении заголовок содержит минимум одну кодовую точку;
  необязательная дата должна быть корректной, приоритет — Low, Normal или High.
  Прошедший срок разрешён: задача может быть просроченной.
- **Сортировка:** сначала незавершённые, внутри каждой группы — высокий приоритет,
  ближайший срок, без срока после датированных внутри приоритета; при равенстве — ID.
- **Поведение:** создание берёт время из Clock и задаёт done=false; изменение полей
  сохраняет время создания и статус. Завершённость можно установить и снять.
- **Почему:** пользователь подтвердил проверки и определённый порядок, согласованный
  с приветствием. Минимум в три символа из парсера на сервис задач не распространяется.

## 24. Создание и изменение событий

- **Дата:** 2026-11-05
- **Статус:** Принято
- **Решение:** заголовок содержит минимум одну кодовую точку; дата обязательна
  и корректна, события в прошлом разрешены. Время необязательно, при наличии —
  от 00:00 до 23:59. Описание необязательно. Повтор — None, Daily, Weekly или Monthly.
- **Изменение:** заменяет поля всей серии с сохранением ID; редактирования отдельных

- **Почему:** пользователь подтвердил явную проверку ввода вместо её отсутствия
  в старом коде и сохранение модели одной записи на всю серию.

## 25. Геонапоминания

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** однократное срабатывание при расстоянии строго меньше 200 м.
  Расстояние вычисляется по сфере (формула гаверсинусов, радиус 6 371 000 м),
  с корректной обработкой перехода долготы через ±180°.
- **Проверки:** название и место содержат минимум одну кодовую точку.
  Координаты необязательны; без них запись хранится, но не срабатывает.
  Числа конечны, широта в пределах −90…90, долгота −180…180; нули допустимы.
- **Срабатывание:** Pending становится Fired до возврата исходной записи для
  уведомления; повторной выдачи нет. Получение позиции и доставка — вне core.
- **Почему:** пользователь подтвердил сохранение радиуса и исправление приближённого
  расчёта старого кода; отсутствие координат уже выражено через optional (решение 14).

## 26. Предупреждения о событиях

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** событие со временем выдаётся при первой проверке, когда до начала
  строго больше 0 и не больше 60 минут, включая последнюю минуту и события
  следующего дня после полуночи. После начала пропущенные предупреждения не выдаются.
- **Без времени:** предупреждать накануне и в день события при первой проверке
  с 08:00 местного времени; поздний запуск выдаёт предупреждение в этот день.
  Повторы обрабатываются CalendarService по тем же правилам.
- **Отметки:** отдельный EventWarningRepository; ключ — ID + дата вхождения + вид
  (перед началом, накануне, сегодня). Изменение времени в этот день не сбрасывает
  отметку перед началом. Отметка сохраняется до возврата предупреждения.
- **Хранение:** сейчас реализация в памяти для тестов; SQLite — этап 3, для сохранения

## 34. Отбор последних сообщений для контекста LLM

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** ChatService::historyMessages принимает явный бюджет текста в кодовых
  точках Unicode без значения по умолчанию. Читаются только сохранённые сообщения
  текущего чата. Отбирается непрерывная последняя часть истории из целых сообщений;
  при первом непоместившемся более старом сообщении отбор останавливается, пропусков нет.
  Результат возвращается по ID от старых сообщений к новым.
- **Недостаточный бюджет:** если последнее сообщение не помещается, вернуть отказ
  с понятной причиной вместо пустой истории или обрезки текста. Нулевой бюджет
  допустим для пустой истории; для непустой действует то же правило вместимости.
- **Сохранность:** отбор возвращает независимые копии и не меняет хранилище.
  Лимиты 40 сообщений и 4000 символов из старого ChatManager не переносятся;
  число сообщений отдельно не ограничивается.
- **Граница:** пока учитывается только текст сообщений, без токенизации и служебных
  частей запроса. Этот бюджет не гарантирует попадания в окно модели. Общая сборка
  с текущим запросом, системным промптом, профилем и сводкой дня, резерв ответа
  и точная проверка токенов относятся к следующим шагам и интеграции llama-server.
  Метод сам не исключает последнее сохранённое сообщение как «текущий запрос»;
  предотвращение его дублирования — обязанность будущей сборки запроса.
- **Проверка на моделях:** пользователь запускает Llama-3.2-3B-Instruct-Q4_K_M
  или qwen2.5-14b-q4_k_m. Размер контекста в предоставленных командах явно не задан,
  фактический размер не проверен; числовой бюджет под эти модели сейчас не фиксируем.
- **Почему:** пользователь доверил технический выбор с последующей проверкой
  на работающем чате. Явный параметр позволяет проверить отбор до подключения
  модели, не выдавая количество символов за точное количество токенов.

## 35. Сборка контекста из готовых данных без записи в хранилище

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** LlmContextBuilder получает инструкции, текущий вопрос, заранее
  выбранные факты по приоритету, готовую сводку дня и снимок истории одного чата.
  Он не обращается к репозиториям и ничего в них не записывает или удаляет.
- **Бюджет:** явный общий предел кодовых точек Unicode без значения по умолчанию.
  Сначала резервируются полные инструкции и текущий вопрос; при нехватке — отказ.
  Затем включаются факты в переданном порядке до первого непоместившегося,
  сводка целиком, затем непрерывная последняя часть истории из целых сообщений.
  Непоместившиеся необязательные части пропускаются; результат сообщает их количество
  и включение сводки. Заголовки разделов и разделители входят в бюджет текста.
- **Порядок запроса:** одно сообщение System с инструкциями, фактами и сводкой;
  затем история User/Assistant по ID, затем полный текущий вопрос User.
  Инструкции задаёт вызывающая сторона, готовый характер ассистента здесь не выбирается.
- **Повтор вопроса:** до его сохранения передаётся только предшествующая история.
  Если он уже записан, вызывающая сторона передаёт currentMessageId; сборщик
  проверяет роль и полный текст, исключает эту запись и более поздние сообщения.
  Более ранние сообщения с таким же текстом не удаляются по совпадению текста.
- **Проверки:** пустые/пробельные инструкции, вопрос и выбранные факты — отказ.
  История должна содержать положительные уникальные ID, один чат и роли User/Assistant;
  несоответствующий ID текущего вопроса также отклоняется.
- **Граница:** пока только сборка из готовых данных. Отбор памяти по теме,
  формулировка промпта, подключение сервисов в приложениях, HTTP, резерв ответа
  и точная проверка токенов модели ещё не реализованы. Полезность состава контекста
  предстоит проверить на работающем чате.
- **Почему:** пользователь подтвердил порядок и сохранность исходных данных;
  текущий вопрос не обрезается и не дублируется, а бюджет проверяется до обращения к модели.

## 36. Локальный отбор фактов по словам и ручным тегам

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** первый вариант отбора памяти работает локально по словам текущего
  вопроса, текста фактов и необязательных тегов пользователя, без дополнительного
  запроса LLM и новых зависимостей. Пользователь одобрил предложенный вариант
  и приоритетные факты «всегда учитывать».
- **Данные:** UserProfileFact содержит полный текст, tags и alwaysInclude.
  Старые вызовы rememberFact с одним текстом создают обычный факт без тегов.
  Теги задаются при добавлении, обрезаются по краям; пустой тег отклоняет запись
  до обращения к хранилищу. Повторы, регистр и внутренние пробелы сохраняются.
- **Поиск:** UserProfileFactSelector получает снимок профиля и текущий вопрос,
  сравнивает целые слова из Unicode-букв и чисел с комбинируемыми знаками.
  Регистр латиницы и кириллицы не учитывается. Оценка — количество разных слов
  вопроса, встретившихся в тексте или тегах; повтор слова не увеличивает оценку.
  Слова многословного тега ищутся отдельно; стоп-списка и морфологии нет.
- **Порядок:** сначала все alwaysInclude в порядке добавления независимо от темы,
  затем факты с ненулевой оценкой по её убыванию; при равенстве — порядок добавления.
  При отсутствии слов или совпадений возвращаются только alwaysInclude.
- **Бюджет:** полные тексты кандидатов передаются в LlmContextBuilder, который
  применяет общий бюджет с оформлением по решению 35. alwaysInclude — приоритет,
  а не гарантия вместимости. Ни отбор, ни сборка не удаляют исходные факты.
- **Граница:** теги назначаются вручную; их автоматическое назначение через LLM
  обсуждается при интеграции. Нет семантического поиска, синонимов и склонений;
  е и ё различаются, Unicode-нормализации нет. Редактирования метаданных через
  сервис и UI пока нет. Отбор и сборка ещё не подключены к приложениям;
  полезность памяти предстоит проверить на работающем чате.
- **Почему:** простой проверяемый вариант без дополнительного обращения к модели;
  ручные теги позволяют добавить альтернативные слова, исходная память сохраняется.

## 37. Полный структурированный ответ LLM и контракт клиента

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** один запрос возвращает полный текст ответа, необязательную оценку
  тона и необязательное предложение записи настроения. Пользователь согласовал
  JSON-формат, первоначальный ответ целиком без потоковой выдачи и отсутствие
  автоматического повтора при ошибке. Поддержка ментора — в том же запросе
  по решению 32; конкретный промпт проверяется при подключении модели.
- **Тон:** Negative/Neutral/Positive либо «не определён»; только для текущей
  реакции, сам не создаёт запись. Оценка явной записи независима от тона.
- **Дневник:** предложение содержит оценку и причину — явная просьба или ответ
  на ожидаемый вечерний опрос. Заметка — полное исходное сообщение пользователя
  без сокращения моделью. Флаг ожидания сам не требует записи: ответ на другую
  тему не должен создавать предложение записи.
- **Контракт:** LlmClient получает LlmRequest с готовыми сообщениями и
  awaitingEveningCheckIn, возвращает LlmResponse либо LlmFailure. Общий complete
  проверяет запрос и типизированный ответ, делает одну попытку через реализацию,
  заполняет заметку исходным текущим User. Пустой ответ, неизвестные оценки
  и причины, EveningCheckInReply без ожидания отклоняются до возврата.
- **Ошибки:** InvalidRequest — неверный запрос, InvalidResponse — неверный JSON
  или результат, Unavailable — недоступность сервиса. Понятная причина без
  частичного ответа и записи настроения. Ошибки памяти и дефекты реализации
  могут передаваться исключениями. JSON описан в `docs/modules/LlmClient.md`;
  его разбор относится к будущему адаптеру infra.

## 38. Промпт ментора и ожидание первого вечернего ответа

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** пользователь согласовал предложенный системный промпт: русский язык,
  обращение на «ты», спокойные краткие ответы, память без выдуманных воспоминаний,
  ненавязчивые упражнения с учётом отказа, разделение тона и явного дневника,
  строгий JSON. При неясной оценке запись не предлагать, при необходимости уточнить.
  Факты и история не заменяют системные правила. Реализация — MentorPrompt.
- **Опрос:** новый текст: «Как прошёл день? 🌙 Если хочешь, расскажи о настроении
  и важных событиях — сохраню твой ответ в дневник настроения.» Старое обещание
  записать прогресс заменено приглашением в дневник.
- **Ожидание:** привязать к чату, дате и сообщению опроса. Рассматривается первый
  следующий User в этом чате. Отказ, другая тема или неясная оценка закрывают
  ожидание при успешной обработке без записи. При ошибке LLM ожидание сохраняется
  для явного повтора; в другую дату недействительно. Переключение чата его
  не переносит. Состояние хранится через EveningCheckInRepository; SQLite — этап 3.
- **Связка:** ConversationService использует ChatService, отбор профиля,
  DailyContextService, LlmContextBuilder, LlmClient, MoodService и сервис опроса.
  Сохраняет User до запроса, исключает его из контекста по ID, получает один
  полный ответ. retryLastMessage повторяет последний User без его дублирования
  после отказа бюджета/LLM; новое сообщение после сбоя не становится первым
  ответом на тот же опрос. Тон сам не создаёт запись.
- **Подтверждение:** модель не заявляет о состоявшейся записи. Код дописывает
  «Настроение сохранено в дневник.» только после успешного MoodService, затем
  сохраняет Assistant. Заметка остаётся полным исходным сообщением по решению 37.
- **Граница:** проверена связка с тестовым клиентом. HTTP, JSON-разбор, качество
  распознавания, поведение ментора на настоящей модели и полезность памяти пока
  не проверены. Приложения не подключены; инструкции описывают желаемое поведение,
  а не доказанное выполнение правил моделью.
- **Ограничение записи:** общей транзакции между репозиториями пока нет;
  технические сбои могут оставлять частичные изменения. Повтор после такого
  сбоя небезопасен; при SQLite нужно согласовать транзакции/восстановление.
- **Почему:** первый ответ не путается с сообщениями другого чата или нового дня,
  отказ не создаёт дневник, подтверждение выдаётся программой после сохранения.

## 39. Автоматические факты из чата с источниками и версиями

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** пользователь согласовал автоматическое сохранение явно сообщённых
  предпочтений, целей, отношений, занятий, биографических сведений и значимых
  событий в том же ответе LLM, без дополнительного запроса и подтверждения каждого
  факта. Предположения, цитаты, вымышленные примеры и мимолётные состояния
  не извлекать; при неясности уточнять. Автоматические теги отложены.
- **Сохранность:** краткий факт не заменяет полный User в истории. ProfileFactSource
  хранит ID чата и сообщения; если это сообщение явно записано в дневник,
  связывается с ID записи. Источник назначает программа. Извлечение факта само
  не создаёт настроение; явные правила дневника сохраняются.
- **Повторы:** автоматический пакет пропускает точные совпадения после trim;
  похожие формулировки не склеиваются. Регистр и внутренние пробелы значимы.
  Ручное rememberFact сохраняет прежнее поведение с повторами.
- **Версии:** у всех добавленных сервисом фактов положительный постоянный ID.
  Явное исправление создаёт новую запись с replacesFactIdentifier, старая получает
  supersededByFactIdentifier и исключается из отбора профиля для LLM. Старые
  текст, источник, теги и приоритет остаются; новая версия наследует теги и приоритет.
  История сообщений не переписывается; промпт учитывает последующие исправления.
- **Безопасность ссылок:** модель может заменить только ID актуального факта,
  реально включённого в бюджет контекста. Метки ID входят в текстовый бюджет.
  Неизвестная/старая цель, две замены одной цели или неоднозначное совпадение
  с другой актуальной записью отклоняют пакет без объединения версий.
  Повтор старого текста без замены не активирует старую версию; явная замена
  текущей версии прежним текстом создаёт новую запись.
- **Контракт LLM:** решение 37 расширено обязательным массивом profile_facts
  с text и replaces_fact_id (null либо ID из контекста). Формат описан в
  `docs/modules/LlmClient.md`; разбор JSON пока отсутствует.
- **Обработка:** ConversationService проверяет пакет до дневника, затем сохраняет
  необязательное настроение, факты с источником и Assistant. Подтверждение
  «Сохранено в памяти» с текстами новых фактов добавляет код после записи.
  Пакет профиля сохраняется одним save; технический сбой по-прежнему может
  оставить частичные изменения между репозиториями. Общей транзакции нет.
- **Граница:** реализованы типизированный контракт и обработка с FakeLlmClient.
  Качество распознавания настоящей моделью не проверено, HTTP и SQLite впереди.
  Интерфейс ручного исправления/удаления ошибочно запомненных фактов ещё нужен;
  удаление и автоматическое назначение тегов в этом шаге не реализуются.
- **Почему:** долговременная память связана с полным источником, исправления
  не уничтожают прошлое, текущий контекст использует актуальные версии.

## 40. Новая пустая SQLite-база, миграции и общие транзакции

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** пользователь согласовал новую схему в отдельном файле и выбрал
  начать пользоваться системой с пустой базой. Импорт данных старого проекта
  исключён из плана. SQLite через Qt Sql в infra подтверждён по решению 5;
  постоянный путь к файлу пока не выбран и задаётся вызывающей стороной.
- **Версии:** целый user_version и последовательные миграции. Базовая версия 1
  помечает пустой файл application_id=0x4D534131 без предметных таблиц. Следующие
  версии добавляются вместе с репозиториями. Неизвестная более новая версия или
  чужая схема отклоняются с понятной ошибкой. Пакет недостающих миграций атомарен.
- **Общие операции:** дневник, профиль, Assistant и снятие ожидания должны
  сохраняться одной транзакцией. User сохраняется до вызова LLM и остаётся
  для повтора; во время ожидания модели транзакция не держится. Публикация
  опроса — отдельная атомарная операция из даты выдачи, сообщения и ожидания.
- **Реализация основы:** SqliteDatabase владеет именованным соединением без
  синглтона, включает внешние ключи, проверяет версию и выполняет SQL-операции.
  Вложенные транзакции используют SAVEPOINT; исключение откатывает изменения.
  При ошибке отката соединение закрывается. Нужен QCoreApplication; владелец
  и запросы используются и уничтожаются в одном потоке.
- **Qt:** Sql добавлен в общий find_package, msa_infra линкуется с Qt6::Sql.
  apps/server получает Qt транзитивно; соответствующее ограничение решения 12
  заменено. core не использует Qt и ничего не знает о SQLite.
- **Граница шага:** готова основа хранения и тесты на временных файлах.
  Репозиториев и предметных таблиц SQLite пока нет, apps/server базу не создаёт.
  Общие транзакции операций ConversationService согласованы, но будут подключены
  после репозиториев; нынешний риск частичных записей ещё не устранён.
- **Почему:** старт с пустыми данными упрощает новую схему; миграции сохраняют
  дальнейшие данные, общая фиксация должна устранить частичные операции чата.

## 41. TransactionRunner для атомарной записи ответа чата

- **Дата:** 2026-11-06
- **Статус:** Принято
- **Решение:** пользователь разрешил принять предложенный TransactionRunner после
  сравнения альтернатив. Интерфейс в core выполняет синхронный callback один раз,
  фиксирует нормальный возврат, откатывает исключение. SqliteDatabase реализует
  его напрямую существующим механизмом SAVEPOINT; тестовая реализация восстанавливает
  снимки чата, дневника, профиля и состояния опроса в памяти.
- **Связка:** обязательная зависимость ConversationService через конструктор;
  все участвующие репозитории используют один исполнитель/соединение. Режима
  выполнения без отката нет. Внутри — проверка пакета фактов, дневник, профиль,
  Assistant и снятие действительного ожидания. Предметный отказ тоже вызывает
  откат и только после него преобразуется обратно в ConversationRejection.
- **Границы:** User записывается до вызова LLM, модель вызывается вне транзакции.
  Подтверждение и результат доступны только после успешной фиксации. После
  подтверждённого отката возможен явный retryLastMessage без дублирования User.
  При отказе отката соединение закрывается; перед повтором нужно восстановить
  соединение и проверить сохранённую историю. Автоматических повторов нет.
- **Почему:** не переносим правила сервисов в инфраструктурный репозиторий ответа
  и не держим транзакцию во время ожидания модели. core не зависит от Qt/SQLite.
- **Отброшено:** отдельный репозиторий атомарного ответа — сейчас усложняет сборку
  изменений нескольких модулей; транзакция вокруг sendMessage — охватывает LLM
  и откатывает User, что противоречит решению 40.
- **Граница шага:** запись ответа атомарна, миграция схемы не требуется.
  Атомарная публикация вечернего опроса остаётся отдельным шагом решения 40.

## 42. Геокодинг, маршруты и погода без неявного местоположения

- **Дата:** 2026-11-07
- **Статус:** Принято
- **Решение:** пользователь согласовал явное местоположение вместо подстановки
  Новосибирска. Nominatim, OSRM и Open-Meteo остаются по решению 8, каждый за
  отдельным интерфейсом core с настоящей и тестовой реализациями.
- **Выбор места:** ближайший кандидат определяется расстоянием по сфере
  относительно явно переданных координат. Без опорного местоположения нужно
  попросить пользователя указать место или передать координаты. Нули допустимы;
  данные без корректных координат не превращаются в точку (0, 0).
- **Маршруты:** сохранить режимы пешком/велосипед/машина, русские инструкции
  и запрет пешего/велосипедного маршрута дальше 200 км по прямой. При недоступности
  OSRM сохранить явно обозначенную приблизительную оценку: расстояние по сфере
  × 1.3, скорости 5/15/40 км/ч. Не выдавать её за маршрут с реальными манёврами.
- **Персонализация:** «личная скорость» из истории прогнозов не переносится:
  прогнозы сервиса не измеряют скорость реальных поездок.
- **Неточные данные поставщика:** пользователь подтвердил оба исправления:
  если OSRM не указал номер съезда, давать общую инструкцию кругового движения,
  не подставлять 1-й съезд. Неизвестный код WMO обозначать как «состояние погоды
  не определено», не относить любой код от 95 к грозе.
- **Граница шага:** три сервиса, выбор ближайшего места, форматирование маршрута
  и сводки погоды, проверки без настоящей сети. История/статистика маршрутов
  и заполнение координат геонапоминаний — отдельный пункт плана; приложения
  и протокол пока не подключены.
- **Nominatim:** пользователь согласовал кэш результатов и ограничение частоты
  по правилам публичного сервиса. Один экземпляр геокодера на приложение,
  не чаще одного запроса в секунду; пользовательские запросы, без фонового обхода.
  Endpoint и User-Agent задаёт приложение. Кэш пока в памяти процесса;
  постоянный кэш и правила фонового геокодинга нужно решить с отдельным шагом.
- **Почему:** не подменять неизвестное местоположение личными значениями,
  не обучаться на собственных прогнозах и отделить HTTP от операций хранилища.

## 43. История расчётов, постоянный кэш и подтверждение точки напоминания

- **Дата:** 2026-11-07
- **Статус:** Принято
- **Решение:** пользователь согласовал уточнённый вариант следующего шага:
  SQLite-история построений, постоянный кэш кандидатов и явный выбор точки.
- **История:** каждый успешный расчёт сохраняет местное время, исходные названия,
  фактические координаты начала/конца, режим, метры, прогноз секунд и approximate.
  История не означает совершённую поездку. Последние пять записей — по ID от новых
  к старым, старые не удаляются. Основные суммы/число построений исключают
  приблизительные оценки; их число показывается отдельно. Реальная скорость
  и пройденное расстояние из прогнозов не вычисляются.
- **Кэш:** сохранять кандидатов, а не выбранную ближайшую точку. Найденные места
  пригодны семь дней, пустые ответы — один час; сетевые и неверные ответы не
  кэшируются. Ключ различает endpoint, запрос и параметры поиска. Для выбора
  ближайшего кандидата каждый раз используются текущие явные координаты.
  Срок проверяется при чтении; принудительной очистки старых ключей пока нет.
- **Геонапоминание:** по явному действию найти и предложить конкретные адреса,
  затем сохранить координаты только после подтверждения выбранного кандидата.
  Автоматический выбор ближайшего для напоминания и периодический обход не нужны.
  Закреплённая точка не меняется при перемещении телефона или обновлении кэша.
- **Сохранность:** поиск выполняется вне транзакции. После поиска и перед
  подтверждением перечитать напоминание; смена текста, места, статуса, типа,
  удаление или появление координат отменяют прежнее предложение. Переданная
  вызывающему коду копия кандидатов не позволяет подменить внутреннее предложение.
- **Реализация:** RouteHistoryRepository и GeocodingCacheRepository имеют SQLite-
  и тестовые реализации; CachedGeocoder оборачивает сетевой Geocoder, заменяя
  прежний бессрочный кэш Nominatim в памяти. NavigationService сохраняет расчёт
  через обязательный RouteHistoryService. PlaceReminderLocationService хранит
  предложения только в рамках живого экземпляра, подтверждение — по ID и индексу.
- **Граница:** библиотеки и тесты. Приложения, UI выбора адреса, GPS и протокол
  ещё не подключены; подтверждение реализовано как контракт core для будущего UI.
  Реальное использование публичных сервисов остаётся пользовательским,
  с общим ограничением частоты Nominatim и атрибуцией при подключении UI.
- **Почему:** история не выдаёт прогнозы за поездки, кэш не закрепляет неверный
  адрес навсегда, напоминание привязывается к выбранному пользователем месту.

## 44. Явный веб-поиск для чата через SearXNG

- **Дата:** 2026-11-07
- **Статус:** Принято
- **Решение:** пользователь согласовал первый вариант с явным запуском поиска,
  SearXNG, интерфейсом в core, HTTP в infra и связкой в ConversationService.
  Это поиск внешней информации в интернете, не поиск по прошлым диалогам.
  История чата и профиль остаются отдельными источниками контекста модели.
- **Запуск:** не переносить широкую эвристику старого CommandParser::needsSearch:
  она включала поиск даже для «почему мне грустно?». Обычные sendMessage/retry
  сеть поиска не вызывают. Отдельные sendMessageWithSearch и
  retryLastMessageWithSearch получают явную поисковую фразу; вызывающий код
  передаёт её по действию пользователя. Профиль и история в поиск не передаются.
- **Выдача:** до трёх пригодных материалов с названием, HTTP(S)-ссылкой и описанием
  до 300 кодовых точек Unicode. Полные страницы не загружаются. Результаты —
  недоверенные внешние данные, не инструкции и не биография пользователя.
- **Контекст:** блок внешних данных передаётся отдельным User перед полным текущим
  вопросом; инструкции System запрещают выполнять указания страниц и извлекать
  из них личные факты/дневник. Семантическое выполнение этих правил настоящей
  моделью пока не проверено. Четырёхполевой JSON-контракт LLM не меняется.
- **Бюджет:** инструкции, текущий вопрос и полный подготовленный блок поиска
  резервируются до необязательных профиля, сводки и истории. Это дополнение
  порядка решения 35 только для явно запрошенного поиска. Если полный блок
  не помещается — отказ до LLM; результаты не выбрасываются молча.
- **Ошибки:** при недоступности/неверной/пустой выдаче возвращать понятную ошибку
  без вызова LLM и без автоматической подстановки ответа без поиска. User уже
  сохранён и остаётся для явного повтора; сеть не выполняется внутри транзакции.
- **Источники:** программа дописывает перечень переданных материалов в Assistant
  и возвращает их также в ConversationReply.searchSources. Список — не доказательство
  истинности ответа и не утверждение, что модель использовала каждый источник.
- **Повтор:** фраза передаётся заново в retryLastMessageWithSearch, User не дублируется.
  Режим/фраза отдельно не сохраняются в БД; обычный retryLastMessage явно означает
  обработку без поиска. Будущий UI должен сохранять выбор операции при повторе.
- **Граница:** библиотеки и проверки без настоящей сети/модели. Адрес SearXNG,
  User-Agent и тайм-аут задаются настройками конструктора; нужен включённый JSON
  в SearXNG. UI, команды запуска поиска и приложения пока не подключены.
  SQLite-схема остаётся версии 12, новой зависимости нет.
- **Почему:** личная беседа не запускает поиск по случайному слову, запросы
  отделены от памяти пользователя, отказ поиска не маскируется ответом модели.

## 48. TCP-транспорт с сигналом запроса и отдельным завершением

- **Дата:** 2026-11-08
- **Статус:** Принято
- **Решение:** пользователь разрешил принять предложенную границу после сравнения
  вариантов. TcpServer в infra обслуживает сокеты, авторизацию и состояние сессии;
  проверенный запрос передаётся через requestReceived, ответ возвращается отдельным
  sendResponse. События после записи публикует вызывающая сторона через publishEvent.
- **Адресация:** завершение требует connectionId и request_id ожидающего запроса.
  ID соединений не переиспользуются в пределах экземпляра транспорта. После обрыва
  поздний ответ отклоняется, даже если новый клиент использует такой же request_id.
  Отключение не означает отмену или откат уже переданной предметной операции.
- **Асинхронность:** сигнал сам по себе не создаёт фонового исполнения. Обработчик
  быстро передаёт работу исполнителю; результат возвращается в поток TcpServer
  через queued-вызов. Все методы транспорта вызываются в его потоке. Выбор исполнителя
  LLM, проверки сроков и владение SQLite согласуются при сборке apps/server;
  существующее соединение SQLite нельзя передавать произвольному рабочему потоку.
- **Альтернативы:** синхронный обработчик блокировал бы обслуживание на время LLM.
  Асинхронный callback работоспособен, но потребовал бы отдельного управления временем
  жизни получателя. Qt-сигнал подходит существующему Qt-транспорту и не добавляет
  интерфейс в core, который ничего не знает о TCP-сессиях.
- **Граница:** библиотечный транспорт и локальные TCP-тесты с тестовым обработчиком.
  Предметные методы, main_chat_id, command.execute и настройки приложения остаются
  следующим шагом; транспорт не объявляет их реализованными.

## 49. Сборка сервера: команды в истории, рабочий HTTP и JSON-настройки

- **Дата:** 2026-11-09
- **Статус:** Принято
- **Решение:** пользователь принял предложенные правила сборки apps/server.
  Успешная command.execute сохраняет исходный User, подтверждение Assistant
  и предметные изменения одной транзакцией. Нераспознанные и отклонённые
  команды не записываются в историю и не запускают LLM.
- **Список задач:** все пункты проверяются до записи; короткий/пустой пункт
  не пропускается с сохранением остальных. Технический сбой откатывает весь список,
  включая сообщения этой команды; прежние задачи остаются.
- **Исполнение:** SQLite, репозитории и предметные записи принадлежат одному
  потоку сервера. HTTP/LLM выполняются отдельным постоянным рабочим потоком без
  доступа к БД. Результат возвращается владельцу. Чтение и проверки сроков
  продолжаются во время ожидания; новая изменяющая операция получает busy до записи.
  Слот транспорта передаёт выполнение отдельному событию и быстро возвращается.
- **Связка синхронных интерфейсов:** NetworkServices ожидает завершение рабочего
  запроса локальным циклом событий владельца. ServerRuntime исключает повторный
  вход в изменяющие операции. Приветствие/опрос откладываются до завершения
  текущей операции, проверки напоминаний/предупреждений продолжаются.
- **Адресация:** отдельный ChatService с явным chat_id на операцию не читает
  и не сохраняет прежний общий выбор. Основной чат хранится по ID в server_state
  миграции 13 и создаётся атомарно; переименование не является сменой идентичности.
- **Маршрут команды:** внешние расчёты выполняются до транзакции; PreparedRoute
  позволяет записать расчёт и сообщения вместе. Постоянный кэш внешних кандидатов
  независим от предметной транзакции и может обновиться даже при отказе команды.
- **Настройки:** строгий JSON, обязательный путь через --config. Относительный
  database_path считается от каталога настроек. Папки автоматически не создаются.
  В репозитории — server.settings.json.example с заглушками, server.local.json
  и файлы SQLite игнорируются. Бюджет символов и лимит генерации задаёт пользователь;
  пример не устанавливает неподтверждённый бюджет модели.
- **Граница:** новый сервер связывает контракт версии 1 с библиотеками. Настоящие
  модели и внешние сервисы, качество ментора/памяти и UI проверяются отдельно.
  Совместимости со старым сервером и импорта прежней базы нет.

## 50. Асинхронный клиент и ограниченное автоматическое переподключение

- **Дата:** 2026-11-09
- **Статус:** Принято
- **Решение:** пользователь выбрал автоматическое переподключение с ограниченной
  задержкой и максимум пятью попытками, затем ручное действие кнопкой.

  ответов/ошибок/событий и автоматически назначаемыми request_id. После соединения

- **Задержка:** возрастающая, с верхним пределом; параметры сроков и задержек

## 57. Голос на ПК: распознавание тоже на C++

- **Дата:** 2026-11-09
- **Статус:** Принято
- **Решение:** пользователь выбрал перенос распознавания речи в C++, отклонив
  предложенное сохранение Python/Vosk отдельным процессом. Python-демон и
  sounddevice не становятся зависимостями нового клиента. Озвучка по плану —
  через Qt TextToSpeech вместо запуска PowerShell.
- **Источник:** с разрешения пользователя прочитаны только voiceinput.h,
  voiceinput.cpp из qt_client_clean/src, qt_client_clean/CMakeLists.txt и
  указанный в нём qt_client_clean/voice_daemon.py старого проекта.
- **Прежнее поведение:** модель Vosk загружается один раз; запись PCM 16 кГц,
  int16, mono заканчивается после одной непустой фразы или STOP. При STOP
  возвращается накопленный FinalResult. Ограничение записи — 30 секунд в C++.
  Распознанный текст выдаётся сигналом; отправка в чат не относится к распознавателю.
  Озвучка прерывает предыдущую речь и допускает явную остановку.
- **Не переносить буквально:** личные пути Python/модели, Python-протокол,
  PowerShell-команды и блокирующее ожидание запуска в потоке интерфейса.
- **Зависимость и изоляция:** пользователь дополнительно согласовал Vosk 0.3.45
  через C API и отдельный C++-процесс. Пакет Windows x64 берётся из официального
  релиза, версия и SHA256 закреплены в cmake/Vosk.cmake. Библиотеку линкует только
  служебный процесс desktop; UI и сервер её не получают.
- **Граница:** core объявляет SpeechRecognizer; infra управляет процессом и
  локальным каналом, UI получает события и испускает действия, apps связывает
  объекты. Модель загружается после явного начала записи и переиспользуется.
  Отмена и зависание завершают процесс; автоматического повторения записи нет.
- **Интерфейс:** фраза дописывается в редактируемый черновик, отправка остаётся
  отдельным действием. Папка модели хранится атомарно в voice.settings.json
  версии 1 рядом с клиентскими настройками; отсутствие файла не включает запись.
  Это применение согласованной границы локального распознавания без отправки в чат.
- **Окружение:** пользователь удалил Qt 6.10.2 и установил полный Qt 6.10.3
  MSVC 2022 64-bit с бинарными Speech и Multimedia. Личные пресеты и шаблон
  используют новый кит; компоненты разных версий не смешиваются.
- **Применение озвучки:** кнопка у сообщения вызывает локальный синтез без
  авточтения и серверных запросов. Новая речь заменяет предыдущую, доступна остановка.
  Для предотвращения записи собственного звука начало диктовки останавливает речь,
  а начало речи отменяет активную диктовку. Это поведение связки приложения;
  интерфейсы распознавания и синтеза остаются независимыми.

## 58. Выбор аудиоустройств и диагностика диктовки

- **Дата:** 2026-11-09
- **Статус:** Принято
- **Запрос пользователя:** после запуска/завершения записи текст не появился;
  пользователь попросил добавить выбор микрофона и динамиков в настройках.
- **Применение:** отдельный выбор входа Vosk и общий выход музыки/озвучки.
  Пустой ID следует системному устройству, явный ID сохраняется без скрытой
  подмены недоступного устройства. Имена не используются как идентификаторы.
- **В рамках существующей архитектуры:** данные в core, QMediaDevices/JSON в
  infra/audio, модель в ui/common, связка в apps/desktop. Отдельный локальный
  audio.settings.json хранит два ID; прежние голосовые и музыкальные настройки
  не меняют схему. Выбор сохраняется по действию и не включает запись.
- **Диагностика:** во время записи отображается уровень PCM, пустой FinalResult
  сопровождается пояснением. Это помогает проверить наличие сигнала, но не
  устанавливает причину проблемы на личном оборудовании автоматически.
- **Вывод озвучки:** для системного варианта сохраняется штатный движок Qt;
  явное устройство на Windows передаётся Qt WinRT через audioDevice. Платформенный
  выбор находится в infra/platform/windows, новых пакетов не требуется.
- **Ручная проверка:** пользователь подтвердил, что распознавание заработало.
  Качество small-ru-0.22 его не устраивает; ru-0.42 оценивается лучше, но долго
  загружается. Пользователь отложил оптимизацию ожидания и подбор другой модели;
  параметры загрузки на этом шаге не меняются.
